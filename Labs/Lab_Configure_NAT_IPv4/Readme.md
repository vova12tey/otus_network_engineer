Цель работы: Настройка и проверка различных типов трансляции сетевых адресов (NAT, PAT, статический NAT) на пограничном маршрутизаторе R1.

Топология: Маршрутизатор R1 (шлюз компании) соединяется с внутренней сетью через интерфейс G0/0/1 и с внешним маршрутизатором провайдера R2 через G0/0/0. R2 имеет Loopback 1, имитирующий внешний сервер. Внутренние ПК (PC-A и PC-B) подключены через коммутаторы S1 и S2.

Часть 1. Создание сети и настройка основных параметров
Шаг 1. Подключение кабелей согласно топологии

В топологии были соединены:

PC-A → S1 (F0/6), PC-B → S2 (F0/18).

S1 (F0/1) ↔ S2 (F0/1) — кабель между коммутаторами.

S1 (F0/5) → R1 (G0/0/1).

R1 (G0/0/0) → R2 (G0/0/0).

Шаг 2. Базовая настройка маршрутизаторов R1 и R2

На R1 и R2 были выполнены стандартные команды: присвоены имена, отключён DNS, установлены пароли class и cisco, настроены баннеры, включено шифрование.
На интерфейсах были назначены IP-адреса согласно таблице:

R1 G0/0/1: 192.168.1.1/24

R1 G0/0/0: 209.165.200.230/29

R2 G0/0/0: 209.165.200.225/29

R2 Loopback 1: 209.165.200.1/27

На R1 был добавлен маршрут по умолчанию через 209.165.200.225, а на R2 — статический маршрут в локальную сеть R1 (192.168.1.0/24 через 209.165.200.230), чтобы ответные пакеты могли возвращаться.

Шаг 3. Настройка коммутаторов S1 и S2

Коммутаторам были присвоены имена, отключён DNS, установлены пароли. Все неиспользуемые порты были отключены для безопасности. В этой лабораторной работе VLAN не настраивались, все порты остались в VLAN 1 по умолчанию.

При отключении неиспользуемых портов на S2 был случайно отключён порт F0/18, который предназначен для подключения PC-B. Это не сразу обнаружилось, но впоследствии привело к проблемам со связью.

Часть 2. Настройка и проверка динамического NAT

Шаг 1. Создание ACL и пула NAT на R1

Был создан стандартный ACL 1, разрешающий трансляцию для всей сети 192.168.1.0/24:
access-list 1 permit 192.168.1.0 0.0.0.255

Создан пул публичных адресов PUBLIC_ACCESS с диапазоном 209.165.200.226 – 209.165.200.228 и маской 255.255.255.248 (соответствующей /29).

Выполнена команда связывания ACL и пула: ip nat inside source list 1 pool PUBLIC_ACCESS.

Интерфейсы помечены: G0/0/1 как ip nat inside, G0/0/0 как ip nat outside.

Шаг 2. Проверка работы динамического NAT

При попытке выполнить пинг с PC-B на адрес 209.165.200.1 (Loopback R2) пинг не проходил — все пакеты терялись.

Диагностика и исправление:

Проверка IP-конфигурации PC-B — оказалось, что на PC-B был установлен режим DHCP, и он имел адрес 0.0.0.0. После переключения на статический IP (адрес 192.168.1.3, шлюз 192.168.1.1) проблема частично решилась.

Проверка статуса портов на S2 — команда show interface status показала, что порт F0/18 (к PC-B) находится в состоянии disabled. После включения порта командой no shutdown на S2 связь восстановилась.

Проверка маршрутизации — на R1 был корректный маршрут по умолчанию, а на R2 — обратный маршрут.

После этих исправлений пинг с PC-B на 209.165.200.1 прошёл успешно.
На R1 команда show ip nat translations показала динамическую трансляцию:
Внутренний локальный адрес 192.168.1.3 транслировался в 209.165.200.226.

Примечание: В Packet Tracer команда show ip nat interface не поддерживалась, поэтому проверка маркировки интерфейсов проводилась через show run | include nat.

Часть 3. Настройка и проверка PAT (NAT с перегрузкой)

Шаг 1. Переход от динамического NAT к PAT с использованием того же пула
На R1 была удалена старая команда связывания ACL и пула:
no ip nat inside source list 1 pool PUBLIC_ACCESS
После этого добавлена команда с ключевым словом overload:
ip nat inside source list 1 pool PUBLIC_ACCESS overload

Проверка работы PAT:
С PC-B был выполнен пинг на 209.165.200.1. Команда show ip nat translations на R1 показала, что все пинги от PC-B используют один и тот же публичный адрес 209.165.200.226, но с разными портами (например, :71, :72, :73, :74). Тайм-аут трансляции сократился до 1 минуты.

Шаг 2. Переход к PAT через внешний интерфейс (более экономичный вариант)

Была удалена конфигурация PAT с пулом и сам пул:
no ip nat inside source list 1 pool PUBLIC_ACCESS overload
no ip nat pool PUBLIC_ACCESS
Затем добавлена команда PAT через внешний интерфейс:
ip nat inside source list 1 interface g0/0/0 overload

Проверка работы PAT через интерфейс:
После повторных пингов с PC-B на 209.165.200.1 таблица NAT показала, что все сеансы теперь используют один внешний IP-адрес интерфейса R1 — 209.165.200.230, но с разными портами (:75, :76, :77, :78). Пинги проходили успешно.

Ошибка на этом этапе:
При попытке очистить таблицу NAT и статистику перед переходом к статическому NAT команды clear ip nat translations и clear ip nat statistics выдали ошибку синтаксиса (Packet Tracer не поддерживает эти команды в полной форме). Однако это не повлияло на дальнейшую настройку, так как статический NAT работает независимо.

Часть 4. Настройка и проверка статического NAT

Шаг 1. Настройка статического сопоставления
На R1 была выполнена команда статического NAT для PC-A:
ip nat inside source static 192.168.1.2 209.165.200.229
Это обеспечило постоянное сопоставление внутреннего адреса PC-A с публичным адресом 209.165.200.229.

Шаг 2. Проверка статического NAT

С маршрутизатора R2 был выполнен пинг на адрес 209.165.200.229. Пинги прошли успешно (3 из 5 пакетов получены, что нормально из-за ARP).

На R1 команда show ip nat translations показала статическую запись:
--- 209.165.200.229 192.168.1.2 --- ---
Это подтвердило, что статический NAT работает, и внешний мир может обращаться к PC-A напрямую.

Итоговый вывод
Лабораторная работа выполнена в полном объёме. Все типы NAT были последовательно настроены и проверены:

Динамический NAT — каждый хост получает уникальный публичный адрес из пула (ограничен 3 адресами).

PAT с пулом — несколько хостов используют один публичный адрес, различаясь портами.

PAT через интерфейс — все хосты используют IP-адрес внешнего интерфейса R1.

Статический NAT — постоянное сопоставление внутреннего адреса с публичным для доступа извне.

В ходе работы были выявлены и исправлены следующие ошибки:

Порт F0/18 на S2 был отключён, что прерывало связь с PC-B.

На PC-B был выбран режим DHCP вместо статического IP.

В Packet Tracer не поддерживались некоторые команды (например, show ip nat interface, clear ip nat translations), но это не помешало успешной настройке.

После исправлений все тесты прошли успешно, и сеть функционирует согласно требованиям лабораторной работы.
